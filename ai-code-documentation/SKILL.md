# AI 程式碼文件規範

## 目的

保持正式原始碼乾淨，避免 AI 產生的解釋性註解在 repo 裡越積越多。

AI 產生的說明、實作筆記、假設與設計理由，應該記錄在：

`docs/AI_NOTES.md`

而不是直接寫進正式原始碼裡。

除非開發者明確要求在原始碼裡加註解，否則本規範適用於所有原始碼。

---

# 核心規則

## 規則 1 — 不要在原始碼裡加不必要的註解

新增或修改原始碼時：

- 不要只是為了解釋程式碼顯而易見的行為就加註解。
- 不要加類似這樣的註解：
  - `// 初始化變數`
  - `// 檢查是否已連線`
  - `// 逐一走訪所有項目`
  - `// 回傳結果`
  - `// 這個方法負責處理...`
- 不要在原始碼裡產生冗長的 AI 說明。
- 不要只因為「AI 產生的實作若有說明會比較好懂」就加註解。

優先讓下列項目本身具備自解釋性，而不是靠解釋性註解：

- 命名
- 方法
- 類別
- 型別
- 結構

---

# 規則 2 — 保留既有的人工註解

不要為了符合本規範而移除、改寫或取代既有的註解。

既有的註解可能是人寫的，可能包含重要的工程知識。

只有在以下情況才可以修改既有註解：

- 開發者明確要求
- 註解內容確實有誤，且修正是必要的
- 開發者要求做文件整理

---

# 規則 3 — 若某段說明真的有價值，另外記錄

有些資訊很有價值，但不一定要嵌入原始碼裡。

例如：

- 非顯而易見的實作決策
- 通訊協定限制
- 硬體限制
- 相容性需求
- workaround（權宜做法）
- 假設條件
- 副作用
- 採用不尋常實作方式的原因
- 開發過程中發現的未記載行為
- 逆向工程得到的行為
- 外部系統的限制

這些情況請記錄到：

`docs/AI_NOTES.md`

不要自動把這類說明加成原始碼註解。

---

# 規則 4 — 不要記錄瑣碎的說明

不要每改一個函式就建立一筆 AI 筆記。

只有在資訊具備有意義的工程參考價值時，才建立 AI 筆記。

例如，以下說明**沒有**價值：

> 這個函式檢查機器人是否已連線。

但以下說明**有**價值：

> 即使內部計算層用的是公尺，機器手臂控制器仍要求座標以毫米為單位輸入。

---

# 規則 5 — 註解不寫變更歷程

註解描述的是「程式碼現在是什麼、為什麼這樣」，不是「程式碼怎麼變成這樣」。變更歷程屬於 git commit 訊息。

新增或修改原始碼時，不要寫：

- 日期戳記：`2026-09-18 新增`、`(2026-09)`
- 變更敘事：「這次改成…」「原本是…後來…」「之前誤判…」「已修正」「先前漏做」
- 狀態標記堆疊：`⚠️ 2026-09-18 …`、`✅ 已驗證`
- commit hash、對話或工作階段的引用：「見今天的討論」「上一輪」

需要記錄「目前尚未驗證」這類狀態時，寫進 `docs/AI_NOTES.md` 的 `狀態` 欄，不要用日期或 emoji 標在原始碼裡。

---

# 既有註解整理（清理模式）

開發者**明確要求**整理既有註解時（例如「把流水帳整理掉」「精簡註解」），才可以依本節修改既有註解，這是規則 2 的例外。沒有要求時不要主動整理。

## 每則註解的處理方式

| 處理 | 適用內容 |
| ---- | -------- |
| **保留** | 一行功能說明；對照說明（例如對應的舊系統函式、RPC 名稱）；單位、範圍、`null` 的意義；`<exception>`；TODO/FIXME；授權聲明 |
| **精簡後保留** | 安全關鍵警告：縮成 1～2 行，寫清楚「不可以做什麼、否則會怎樣」，細節移到 AI_NOTES |
| **移到 AI_NOTES 後刪除** | 設計理由、協定或硬體的實測發現、未驗證的假設、事故教訓、與外部文件的差異、刻意不做某件事的原因 |
| **直接刪除** | 規則 5 列出的變更歷程；重述程式碼；對話式說明；已經過時或和程式碼矛盾的描述（矛盾時先跟開發者確認） |

一則註解常同時包含多種內容，要拆開處理：例如「⚠️ 2026-09-18 新增：控制器把目標解讀成 TCP，尚未實機驗證」→ 日期刪除、「控制器把目標解讀成 TCP」寫進 AI_NOTES（狀態 `未驗證`）、原始碼只留一行功能說明。

## XML 文件註解的保留標準

- `<summary>`：1～2 行，說明做什麼；有對照說明時一併放在這裡。
- `<param>`、`<returns>`：只在單位、座標系、範圍、`null`/預設值意義不明顯時才寫。只寫部分參數是刻意的；專案若開啟文件產生（`GenerateDocumentationFile`）並把 CS1573 視為錯誤，才需要補齊全部參數。
- `<exception>`：保留。
- `<remarks>`：原則上移到 AI_NOTES；只有安全關鍵警告可以留下精簡版。

## 專案規範優先

專案指示檔（例如 `CLAUDE.md`）明確要求在原始碼標示的資訊，照專案規範保留，但去掉日期與過程敘事。例如專案要求「硬體常數須標明官方確認值或概估值」，就保留「（官方規格）」「（實測校正值）」這類短標示，校正過程移到 AI_NOTES。

## 流程

1. 掃描：列出每個檔案的註解行數與變更歷程標記數量（日期、⚠️/✅、commit hash、「原本/後來/改成/已修正」等），先跟開發者確認範圍與保留原則。
2. 分批：依專案或分層分批處理，大檔案可以再拆；有版本控制時開新分支、每批一個 commit。
3. 每一批：先把要保留的知識寫進 AI_NOTES，再刪原始碼註解；**只改註解，不改程式行為**。
4. 驗證每一批：
   - **只改了註解**：把修改前後的檔案去掉註解與空白行後比對，必須完全相同。
   - **建置與測試**通過。
   - **註解內的引用仍有效**：改寫時新增或改動的 `<see cref>` 等引用，要確認目標名稱存在。沒有開啟文件產生的專案，寫錯的 cref 不會出現警告，可暫時以文件產生模式建置來檢查（例如 `dotnet build -p:GenerateDocumentationFile=true`）。
5. 專案指示檔若寫著「詳細說明在原始碼註解裡」，同步改成指向 `docs/AI_NOTES.md`。
6. 回報：列出整理過程中發現、但不在範圍內所以沒有修正的問題，例如與程式碼矛盾的註解、專案指示檔裡過時的描述。

## 整理時常見的情況

- **過時或矛盾的註解**：註解描述的行為與程式碼不符（例如寫「零參數」但方法已有參數）。屬於明顯過時的直接刪除；涉及行為判斷（例如兩處說法互相矛盾、不確定哪個才對）時，改成與程式碼一致的描述，並在回報中列出讓開發者確認。
- **放錯位置的文件註解**：例如兩段 `<summary>` 疊在同一個成員上，其中一段其實在描述下一個方法。移到正確的成員上（只移動註解，不改程式碼）。
- **AI_NOTES 行號**：從宣告處（不是呼叫處）找行號；整理後原始碼行號會大幅變動，所以每批結束時重新計算。由原始碼產生器產生的成員（例如 `[ObservableProperty]` 由欄位 `initialValue` 產生屬性 `InitialValue`），`函式` 欄填原始碼裡實際存在的欄位名稱。
- **非程式碼檔案（XAML、設定檔等）**：`命名空間` 填 `—`，`類別` 填資源鍵（例如 `x:Key` 或 `TargetType`），整份檔案的筆記兩者都填 `—`。依專案規範本來就要寫在資源檔裡的對照說明（例如色票「這個顏色用在哪裡」、依使用頁面分的 region 標題）屬於必要說明，保留。
- **測試基準本身就有失敗**：先在未修改的版本（例如另開 worktree 檢出 main）跑一次測試，確認失敗原本就存在；之後每批只允許這些已知失敗，出現其他失敗就停止、不 commit。驗證與 commit 不要用 `;` 串接，避免驗證失敗仍然 commit。已知失敗記錄在 AI_NOTES 並在最後回報。

# AI_NOTES.md 格式

## 語言設定

AI_NOTES.md 支援兩種語言：

| 設定值 | 語言 | 範本 |
| ------ | ---- | ---- |
| `zh-TW`（預設） | 繁體中文 | 本 skill 的 `docs/AI_NOTES.md` |
| `en` | 英文 | 本 skill 的 `docs/AI_NOTES.en.md` |

依下列順序決定語言，採用第一個符合的：

1. **開發者在對話中明確指定**，例如「AI_NOTES 用英文寫」。
2. **專案指示檔的設定**：專案的 `CLAUDE.md`（或 `AGENTS.md` 等該工具使用的專案指示檔）中有一行：
   ```text
   AI_NOTES_LANGUAGE: en
   ```
   值為 `zh-TW` 或 `en`。
3. **既有的 `docs/AI_NOTES.md`**：標題是 `# AI Implementation Notes` 視為英文；`# AI 開發筆記` 視為繁體中文。
4. **預設**：繁體中文（`zh-TW`）。

規則：

- 選定的語言適用於 AI_NOTES.md 的全部內容：標題、規則、表頭、類型、狀態、說明。
- 程式碼識別名稱一律保留原文，例如檔案路徑、命名空間、類別、函式、RPC/指令名稱、設定鍵。
- 同一份 AI_NOTES.md 不可混用兩種語言。設定（第 1、2 點）與既有檔案的語言不同時，先詢問開發者是否要把既有檔案整份轉換，不要自行混寫。
- 依 `agents/review-ai-comments.md` 產出的審查報告也使用同一個語言。

## 建立檔案

如果 `docs/AI_NOTES.md` 不存在，就依語言設定，從對應的範本建立它（複製時去掉最後的「範例」/「Example」段落）。不論哪種語言，檔名都是 `docs/AI_NOTES.md`。

## 表格結構

| 欄位 | 繁體中文 | English |
| ---- | -------- | ------- |
| 表頭 | `檔案 \| 命名空間 \| 類別 \| 函式 \| 行號 \| 類型 \| 狀態 \| 說明` | `File \| Namespace \| Class \| Function \| Line \| Type \| Status \| Note` |

`類型` 的值：

| 繁體中文 | English | 用途 |
| -------- | ------- | ---- |
| `限制` | `Constraint` | 實作或硬體限制 |
| `協定` | `Protocol` | 通訊或協定要求 |
| `設計` | `Design` | 設計決策或架構理由 |
| `硬體` | `Hardware` | 硬體特有行為 |
| `權宜做法` | `Workaround` | 為了外部或舊系統限制採取的做法 |
| `效能` | `Performance` | 效能相關的實作細節 |
| `相容性` | `Compatibility` | 相容性要求 |
| `校正` | `Calibration` | 校正或機台特有資訊 |
| `安全` | `Safety` | 安全關鍵資訊 |

`狀態` 的值：

| 繁體中文 | English | 意義 |
| -------- | ------- | ---- |
| `使用中` | `Active` | 目前有效 |
| `已棄用` | `Deprecated` | 已不再適用，保留作為歷史紀錄 |
| `已驗證` | `Verified` | 已在實機或真實環境確認 |
| `未驗證` | `Unverified` | 尚未在實機或真實環境確認 |
| `暫時` | `Temporary` | 權宜性質，之後應該被正式做法取代 |

- `已驗證`/`Verified` 只用於已在實機或真實環境確認的項目；只有單元測試的不算。
- 沒有對應函式時（例如類別或 record 本身），`函式`/`Function` 欄填 `—`。
- 同一個類別有多筆筆記、且都屬於整個類別時，可以合併成一筆，`函式` 欄填 `—`。

## 筆記多時的分組

筆記超過約 20 筆時，在「筆記」段落底下依專案（或模組）分組，每組用 `###` 標題加一張獨立表格，例如：

```markdown
## 筆記

### MyApp.Core

| 檔案 | 命名空間 | 類別 | 函式 | 行號 | 類型 | 狀態 | 說明 |
| ---- | -------- | ---- | ---- | ---: | ---- | ---- | ---- |
| ... |

### MyApp.Protocols

| 檔案 | ... |
```

組內依檔案路徑排序。新增筆記時放進對應的組，不要附加在檔案最後。

## 說明欄的寫法

- 寫事實與理由，不寫變更歷程（同規則 5）。需要時間脈絡時，只寫「何時確認」這種對讀者有用的資訊，例如「已用 9 組姿態交叉驗證」，不寫「2026-09-18 新增」。
- 一筆筆記只講一件事；同一個方法有兩個獨立的發現，就寫兩筆。
- 引用外部文件時寫出文件名稱與章節，方便追查。
