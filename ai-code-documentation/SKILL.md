# AI 程式碼文件規範

保持正式原始碼乾淨，避免 AI 產生的解釋性註解在 repo 裡越積越多。AI 產生的說明、假設與設計理由記錄在 `docs/AI_NOTES.md`，不寫進原始碼。

開發者明確要求在原始碼加註解時（例如「幫這個方法加 XML 文件註解」），照要求做。

## 規則 1 — 不要在原始碼裡加不必要的註解

- 不要為了解釋顯而易見的行為加註解，例如 `// 初始化變數`、`// 檢查是否已連線`、`// 逐一走訪所有項目`、`// 回傳結果`、`// 這個方法負責處理...`。
- 不要在原始碼裡寫冗長的 AI 說明，也不要只因為「有說明比較好懂」就加註解。
- 優先用命名、方法、類別、型別與結構讓程式碼自我說明。
- 例外：安全或硬體關鍵的警告可以留在原始碼，縮成 1～2 行，寫清楚「不可以做什麼、否則會怎樣」，細節寫進 AI_NOTES。

## 規則 2 — 保留既有註解

既有註解一律視為人工註解，可能包含重要的工程知識。不要為了符合本規範而移除、改寫或取代。

只有在以下情況才可以修改既有註解：

- 開發者明確要求，包括要求整理註解（見下方「整理既有註解」）
- 註解內容確實有誤，且修正是必要的

## 規則 3 — 只把有價值的知識記到 AI_NOTES

不要每改一個函式就寫一筆筆記。只記錄讀原始碼看不出來、且有工程參考價值的資訊，例如：

- 非顯而易見的實作決策、採用不尋常做法的原因
- 通訊協定、硬體、外部系統的限制
- 相容性需求、權宜做法（workaround）
- 假設條件、副作用
- 開發過程中發現或逆向工程得到的未記載行為

| 沒有價值 | 有價值 |
| -------- | ------ |
| 這個函式檢查機器人是否已連線。 | 即使內部計算層用的是公尺，機器手臂控制器仍要求座標以毫米為單位輸入。 |

不要把這類說明自動加成原始碼註解。

## 規則 4 — 維護既有筆記

- 修改原始碼前先查 `docs/AI_NOTES.md`，看是否有筆記受到影響。
- 同一個問題已有筆記時，更新既有筆記，不要建立重複的筆記。
- 限制或做法有變動時，更新筆記內容與 `狀態`；已不適用的改成 `已棄用`。
- 不要記錄 AI 的暫時推理過程或對話式說明。

## 規則 5 — 註解不寫變更歷程

註解描述的是「程式碼現在是什麼、為什麼這樣」，不是「程式碼怎麼變成這樣」。變更歷程屬於 git commit 訊息。不要寫：

- 日期戳記：`2026-09-18 新增`、`(2026-09)`
- 變更敘事：「這次改成…」「原本是…後來…」「之前誤判…」「已修正」「先前漏做」
- 狀態標記堆疊：`⚠️ 2026-09-18 …`、`✅ 已驗證`
- commit hash、對話或工作階段的引用：「見今天的討論」「上一輪」

需要記錄「尚未驗證」這類狀態時，寫進 AI_NOTES 的 `狀態` 欄。

## 整理與審查既有註解

- 開發者**明確要求**整理既有註解時（例如「把流水帳整理掉」「精簡註解」），先讀本 skill 的 `references/cleanup.md`，依其流程處理。沒有要求時不要主動整理。
- 開發者要求找出多餘的 AI 註解（只出報告、不修改）時，依本 skill 的 `agents/review-ai-comments.md` 審查。

# AI_NOTES.md 格式

## 語言設定

支援 `zh-TW`（繁體中文，預設）與 `en`（英文）。依序採用第一個符合的：

1. 開發者在對話中明確指定，例如「AI_NOTES 用英文寫」。
2. 專案指示檔（`CLAUDE.md`、`AGENTS.md` 等）中的 `AI_NOTES_LANGUAGE: en` 或 `AI_NOTES_LANGUAGE: zh-TW`。
3. 既有 `docs/AI_NOTES.md` 的標題：`# AI Implementation Notes` 為英文，`# AI 開發筆記` 為繁體中文。
4. 預設繁體中文。

- 整份檔案（標題、表頭、類型、狀態、說明）使用同一種語言；程式碼識別名稱（檔案路徑、命名空間、類別、函式、RPC/指令名稱、設定鍵）保留原文。
- 第 1、2 點指定的語言與既有檔案不同時，先詢問開發者是否整份轉換，不要混寫。
- 審查報告也使用同一種語言。

## 建立檔案

`docs/AI_NOTES.md` 不存在時，從本 skill 的範本建立：繁體中文用 `docs/AI_NOTES.md`，英文用 `docs/AI_NOTES.en.md`，複製時去掉最後的「範例」/「Example」段落。兩種語言的檔名都是 `docs/AI_NOTES.md`。

## 欄位

| 語言 | 表頭 |
| ---- | ---- |
| 繁體中文 | `檔案 \| 命名空間 \| 類別 \| 函式 \| 行號 \| 類型 \| 狀態 \| 說明` |
| English | `File \| Namespace \| Class \| Function \| Line \| Type \| Status \| Note` |

`類型` 的值：

| 繁體中文 | English | 用途 |
| -------- | ------- | ---- |
| `限制` | `Constraint` | 實作或硬體限制 |
| `協定` | `Protocol` | 通訊或協定要求 |
| `設計` | `Design` | 設計決策或架構理由 |
| `硬體` | `Hardware` | 硬體特有行為 |
| `權宜做法` | `Workaround` | 為了外部或舊系統限制採取的做法 |
| `效能` | `Performance` | 效能相關的實作細節 |
| `相容性` | `Compatibility` | 相容性要求 |
| `校正` | `Calibration` | 校正或機台特有資訊 |
| `安全` | `Safety` | 安全關鍵資訊 |

`狀態` 的值：

| 繁體中文 | English | 意義 |
| -------- | ------- | ---- |
| `使用中` | `Active` | 目前有效 |
| `已棄用` | `Deprecated` | 已不再適用，保留作為歷史紀錄 |
| `已驗證` | `Verified` | 已在實機或真實環境確認；只有單元測試的不算 |
| `未驗證` | `Unverified` | 尚未在實機或真實環境確認 |
| `暫時` | `Temporary` | 權宜性質，之後應該被正式做法取代 |

- `行號` 取宣告處（不是呼叫處），僅供參考；辨識時以檔案、命名空間、類別、函式搭配說明為準。
- 沒有對應函式時（例如類別或 record 本身），`函式` 欄填 `—`。同一個類別有多筆都屬於整個類別的筆記，可以合併成一筆。
- 非程式碼檔案（XAML、設定檔等）：`命名空間` 填 `—`，`類別` 填資源鍵（例如 `x:Key` 或 `TargetType`）；整份檔案的筆記兩者都填 `—`。

## 筆記多時的分組

筆記超過約 20 筆時，在「筆記」段落底下依專案（或模組）分組，每組用 `###` 標題加一張獨立表格，組內依檔案路徑排序。新增筆記時放進對應的組，不要附加在檔案最後。

```markdown
## 筆記

### MyApp.Core

| 檔案 | 命名空間 | 類別 | 函式 | 行號 | 類型 | 狀態 | 說明 |
| ---- | -------- | ---- | ---- | ---: | ---- | ---- | ---- |
| ... |

### MyApp.Protocols
...
```

## 說明欄的寫法

- 一筆筆記只講一件事；同一個方法有兩個獨立的發現，就寫兩筆。
- 需要時間脈絡時，只寫對讀者有用的資訊（例如「已用 9 組姿態交叉驗證」），不寫變更歷程（同規則 5）。
- 引用外部文件時寫出文件名稱與章節，方便追查。
