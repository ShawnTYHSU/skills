# AI 程式碼文件規範

## 目的

保持正式原始碼乾淨，避免 AI 產生的解釋性註解在 repo 裡越積越多。

AI 產生的說明、實作筆記、假設與設計理由，應該記錄在：

`docs/AI_NOTES.md`

而不是直接寫進正式原始碼裡。

除非開發者明確要求在原始碼裡加註解，否則本規範適用於所有原始碼。

---

# 核心規則

## 規則 1 — 不要在原始碼裡加不必要的註解

新增或修改原始碼時：

- 不要只是為了解釋程式碼顯而易見的行為就加註解。
- 不要加類似這樣的註解：
  - `// 初始化變數`
  - `// 檢查是否已連線`
  - `// 逐一走訪所有項目`
  - `// 回傳結果`
  - `// 這個方法負責處理...`
- 不要在原始碼裡產生冗長的 AI 說明。
- 不要只因為「AI 產生的實作若有說明會比較好懂」就加註解。

優先讓下列項目本身具備自解釋性，而不是靠解釋性註解：

- 命名
- 方法
- 類別
- 型別
- 結構

---

# 規則 2 — 保留既有的人工註解

不要為了符合本規範而移除、改寫或取代既有的註解。

既有的註解可能是人寫的，可能包含重要的工程知識。

只有在以下情況才可以修改既有註解：

- 開發者明確要求
- 註解內容確實有誤，且修正是必要的
- 開發者要求做文件整理

---

# 規則 3 — 若某段說明真的有價值，另外記錄

有些資訊很有價值，但不一定要嵌入原始碼裡。

例如：

- 非顯而易見的實作決策
- 通訊協定限制
- 硬體限制
- 相容性需求
- workaround（權宜做法）
- 假設條件
- 副作用
- 採用不尋常實作方式的原因
- 開發過程中發現的未記載行為
- 逆向工程得到的行為
- 外部系統的限制

這些情況請記錄到：

`docs/AI_NOTES.md`

不要自動把這類說明加成原始碼註解。

---

# 規則 4 — 不要記錄瑣碎的說明

不要每改一個函式就建立一筆 AI 筆記。

只有在資訊具備有意義的工程參考價值時，才建立 AI 筆記。

例如，以下說明**沒有**價值：

> 這個函式檢查機器人是否已連線。

但以下說明**有**價值：

> 即使內部計算層用的是公尺，機器手臂控制器仍要求座標以毫米為單位輸入。

---

# AI_NOTES.md 格式

## 語言設定

AI_NOTES.md 支援兩種語言：

| 設定值 | 語言 | 範本 |
| ------ | ---- | ---- |
| `zh-TW`（預設） | 繁體中文 | 本 skill 的 `docs/AI_NOTES.md` |
| `en` | 英文 | 本 skill 的 `docs/AI_NOTES.en.md` |

依下列順序決定語言，採用第一個符合的：

1. **開發者在對話中明確指定**，例如「AI_NOTES 用英文寫」。
2. **專案指示檔的設定**：專案的 `CLAUDE.md`（或 `AGENTS.md` 等該工具使用的專案指示檔）中有一行：
   ```text
   AI_NOTES_LANGUAGE: en
   ```
   值為 `zh-TW` 或 `en`。
3. **既有的 `docs/AI_NOTES.md`**：標題是 `# AI Implementation Notes` 視為英文；`# AI 開發筆記` 視為繁體中文。
4. **預設**：繁體中文（`zh-TW`）。

規則：

- 選定的語言適用於 AI_NOTES.md 的全部內容：標題、規則、表頭、類型、狀態、說明。
- 程式碼識別名稱一律保留原文，例如檔案路徑、命名空間、類別、函式、RPC/指令名稱、設定鍵。
- 同一份 AI_NOTES.md 不可混用兩種語言。設定（第 1、2 點）與既有檔案的語言不同時，先詢問開發者是否要把既有檔案整份轉換，不要自行混寫。
- 依 `agents/review-ai-comments.md` 產出的審查報告也使用同一個語言。

## 建立檔案

如果 `docs/AI_NOTES.md` 不存在，就依語言設定，從對應的範本建立它（複製時去掉最後的「範例」/「Example」段落）。不論哪種語言，檔名都是 `docs/AI_NOTES.md`。

## 表格結構

| 欄位 | 繁體中文 | English |
| ---- | -------- | ------- |
| 表頭 | `檔案 \| 命名空間 \| 類別 \| 函式 \| 行號 \| 類型 \| 狀態 \| 說明` | `File \| Namespace \| Class \| Function \| Line \| Type \| Status \| Note` |

`類型` 的值：

| 繁體中文 | English | 用途 |
| -------- | ------- | ---- |
| `限制` | `Constraint` | 實作或硬體限制 |
| `協定` | `Protocol` | 通訊或協定要求 |
| `設計` | `Design` | 設計決策或架構理由 |
| `硬體` | `Hardware` | 硬體特有行為 |
| `權宜做法` | `Workaround` | 為了外部或舊系統限制採取的做法 |
| `效能` | `Performance` | 效能相關的實作細節 |
| `相容性` | `Compatibility` | 相容性要求 |
| `校正` | `Calibration` | 校正或機台特有資訊 |
| `安全` | `Safety` | 安全關鍵資訊 |

`狀態` 的值：

| 繁體中文 | English | 意義 |
| -------- | ------- | ---- |
| `使用中` | `Active` | 目前有效 |
| `已棄用` | `Deprecated` | 已不再適用，保留作為歷史紀錄 |
| `已驗證` | `Verified` | 已在實機或真實環境確認 |
| `未驗證` | `Unverified` | 尚未在實機或真實環境確認 |
| `暫時` | `Temporary` | 權宜性質，之後應該被正式做法取代 |

- `已驗證`/`Verified` 只用於已在實機或真實環境確認的項目；只有單元測試的不算。
- 沒有對應函式時（例如類別或 record 本身），`函式`/`Function` 欄填 `—`。
