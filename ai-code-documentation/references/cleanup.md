# 整理既有註解（清理模式）

開發者**明確要求**整理既有註解時才使用本流程，這是 `SKILL.md` 規則 2 的例外。沒有要求時不要主動整理。

## 每則註解的處理方式

| 處理 | 適用內容 |
| ---- | -------- |
| **保留** | 一行功能說明；對照說明（例如對應的舊系統函式、RPC 名稱）；單位、範圍、`null` 的意義；`<exception>`；TODO/FIXME；授權聲明 |
| **精簡後保留** | 安全關鍵警告：縮成 1～2 行，寫清楚「不可以做什麼、否則會怎樣」，細節移到 AI_NOTES，警告結尾加「詳見 docs/AI_NOTES.md」 |
| **移到 AI_NOTES 後刪除** | 設計理由、協定或硬體的實測發現、未驗證的假設、事故教訓、與外部文件的差異、刻意不做某件事的原因 |
| **直接刪除** | 規則 5 列出的變更歷程；重述程式碼；對話式說明；已經過時或和程式碼矛盾的描述（矛盾時先跟開發者確認） |

一則註解常同時包含多種內容，要拆開處理：例如「⚠️ 2026-09-18 新增：控制器把目標解讀成 TCP，尚未實機驗證」→ 日期刪除、「控制器把目標解讀成 TCP」寫進 AI_NOTES（狀態 `未驗證`）、原始碼只留一行功能說明。

## 專案規範優先

專案指示檔（例如 `CLAUDE.md`）明確要求在原始碼標示的資訊，照專案規範保留，但去掉日期與過程敘事。例如專案要求「硬體常數須標明官方確認值或概估值」，就保留「（官方規格）」「（實測校正值）」這類短標示，校正過程移到 AI_NOTES。

依專案規範本來就要寫在資源檔裡的對照說明（例如色票「這個顏色用在哪裡」、依使用頁面分的 region 標題）屬於必要說明，保留。

## 流程

1. **掃描**：列出每個檔案的註解行數與變更歷程標記數量（日期、⚠️/✅、commit hash、「原本/後來/改成/已修正」等），先跟開發者確認範圍與保留原則。方案檔（例如 `.sln`）可能引用 repo 以外的專案（例如相鄰 repo），只處理 repo 內的檔案，驗證時也要排除外部專案的警告。
2. **確認測試基準**：在未修改的版本（例如另開 worktree 檢出 main）先建置並跑一次測試。原本就失敗的測試記為已知失敗，記錄在 AI_NOTES 並在最後回報。
3. **分批**：依專案或分層分批處理，大檔案可以再拆；有版本控制時開新分支、每批一個 commit。
4. **每一批**：先把要保留的知識寫進 AI_NOTES，再刪原始碼註解；**只改註解，不改程式行為**。
5. **驗證每一批**，全部通過才 commit（驗證與 commit 不要用 `;` 串接，避免驗證失敗仍然 commit；驗證腳本的每一步，包括重新產生 AI_NOTES，失敗都要中止）：
   - **只改了註解**：把修改前後的檔案去掉註解與空白行後比對，必須完全相同。
   - **建置與測試**通過；只允許第 2 步記下的已知失敗，出現其他失敗就停止。
   - **註解內的引用仍有效**：改寫時新增或改動的引用（例如 `<see cref>`），要確認目標名稱存在。
   - **AI_NOTES 行號**：整理後原始碼行號會大幅變動，每批結束時重新計算有填行號的筆記。
6. 專案指示檔若寫著「詳細說明在原始碼註解裡」，同步改成指向 `docs/AI_NOTES.md`。
7. **回報**：列出整理過程中發現、但不在範圍內所以沒有修正的問題，例如與程式碼矛盾的註解、專案指示檔裡過時的描述。

## 常見情況

- **過時或矛盾的註解**：註解描述的行為與程式碼不符（例如寫「零參數」但方法已有參數）。明顯過時的直接刪除；涉及行為判斷（例如兩處說法互相矛盾、不確定哪個才對）時，改成與程式碼一致的描述，並在回報中列出讓開發者確認。
- **註解之間的引用**：例如「理由同 X 上方說明」，而 X 的說明已刪除或精簡。把引用端改成不依賴其他註解的完整說明。
- **驗證狀態互相矛盾**：例如一處寫「完全沒有實機測試過」，另一處卻記錄了實機測試結果。原始碼刪除這類狀態描述，在 AI_NOTES 的 `狀態` 欄統一記錄，並在回報中列出。
- **既有 AI_NOTES 格式較舊**：保留所有筆記內容，把標題、表頭與段落改成目前範本的格式，不要另開新檔。
- **放錯位置的文件註解**：例如兩段文件註解疊在同一個成員上，其中一段其實在描述下一個方法。移到正確的成員上（只移動註解，不改程式碼）。

## .NET / C# 專案

### XML 文件註解的保留標準

- `<summary>`：1～2 行，說明做什麼；有對照說明時一併放在這裡。
- `<param>`、`<returns>`：只在單位、座標系、範圍、`null`/預設值意義不明顯時才寫。只寫部分參數是刻意的；專案若開啟文件產生（`GenerateDocumentationFile`）並把 CS1573 視為錯誤，才需要補齊全部參數。
- `<exception>`：保留。
- `<remarks>`：原則上移到 AI_NOTES；只有安全關鍵警告可以留下精簡版。

### 其他

- **檢查 `<see cref>`**：沒有開啟文件產生的專案，寫錯的 cref 不會出現警告，可暫時以文件產生模式建置來檢查：`dotnet build -p:GenerateDocumentationFile=true -p:NoWarn=CS1591`（CS1591 是「缺少文件註解」，與 cref 無關）。
- **指向上層或外部專案的 cref**：下層專案（例如 Abstractions）無法參考上層（例如 Core）或其他 repo 的型別，這類 `<see cref>` 永遠無法解析，改用 `<c>型別名稱</c>`。
- **原始碼產生器產生的成員**：例如 `[ObservableProperty]` 由欄位 `initialValue` 產生屬性 `InitialValue`，AI_NOTES 的 `函式` 欄填原始碼裡實際存在的欄位名稱。
